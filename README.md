**1 — проєктування схеми**
1. Які сутності стали вузлами, а які — ребрами? Чому?
Вузли (User, Movie, Genre): сутності з власною ідентичністю та атрибутами, між якими проходять шляхи й агрегації.
Ребра (RATED, HAS_GENRE): зв'язки та дії між сутностями — «користувач оцінив фільм» (з rating і timestamp) та «фільм має жанр».

2. Оцінка користувача за фільм — це ребро (User)-[:RATED]->(Movie) чи окремий вузол (Rating)? Аргументуйте своє рішення. Це не риторичне запитання: в обох підходів є реальні trade-off-и.
Обране рішення — ребро (:User)-[:RATED {rating, timestamp}]->(:Movie): менше хопів у запитах на спільні фільми, рекомендації та найкоротший шлях; менше об'єктів у базі на понад 1 млн оцінок і простіше завантаження.
Коли вигідніший вузол (:Rating): якщо один користувач може ставити кілька оцінок тому самому фільму або якщо сама оцінка отримує власні зв'язки (теги, рецензії, лайки оцінок тощо).

3. Чому жанри фільму вигідніше зберігати як окремі вузли (Genre), а не як список у властивості вузла Movie?
Прямий і швидкий обхід: старт одразу з вузла (:Genre {name}) для фільтрів і агрегацій за жанром без перевірки масивів на кожному фільмі.
Простіші групування та цілісність: не потрібен UNWIND при кожній агрегації по жанрах, назва жанру існує в одному екземплярі, а в майбутньому до Genre легко додати власні зв'язки чи властивості.

**Схема графа**
```text
 -----------------------------------
|               User                |
 -----------------------------------
| userId : Integer (UNIQUE)         |
| gender : String                   |
| age : Integer                     |
| occupation : Integer              |
 ----------------------------------- 
                  |
                  |   [:RATED]
                  |   rating : Integer
                  |   timestamp : Integer
                  v
 -----------------------------------         [:HAS_GENRE]             -------------------
|               Movie               | -----------------------------> |       Genre       |
 -----------------------------------                                  -------------------
| movieId : Integer (UNIQUE)        |                                | name : String     |
| title : String                    |                                |        (UNIQUE)   |
| year : Integer                    |                                 -------------------
 -----------------------------------
```

**Компоненти схеми**
* **`:User`** — користувач (`userId`, `gender`, `age`, `occupation`)
* **`:Movie`** — фільм (`movieId`, `title`, `year`)
* **`:Genre`** — жанр (`name`)
* **`[:RATED]`** — напрямок від `(:User)` до `(:Movie)` із властивостями `rating` та `timestamp`
* **`[:HAS_GENRE]`** — напрямок від `(:Movie)` до `(:Genre)`

**2 — Завантаження даних**
Цей варіант скрипту був обраний так, щоб завантаження повністю відповідало схемі графа й було безпечним при повторному запуску:
* Читання напряму з GitHub (raw.githubusercontent.com): дозволяє брати актуальні users.csv і movies.csv одразу з репозиторію без ручного копіювання файлів у локальну чи Docker-папку import після кожного оновлення.
* Фільтрація пустих/NULL значень і явне приведення типів (toInteger): у CSV усі поля приходять як рядки, тому перевірка IS NOT NULL AND trim(...) <> '' та перетворення ID, віку, професії й року в цілі числа захищають від «битих» вузлів і помилок типізації.
* Виділення year і підготовка genres на Movie: регулярний вираз .*\\(\\d{4}\\)\\s*$ дістає рік у дужках із кінця назви фільму в окрему властивість m.year (згідно зі схемою), а split(row.genres, '|') формує список жанрів.
* Розділення створення Movie та Genre + [:HAS_GENRE] на окремі блоки з MERGE: спочатку чисто створюються вузли User і Movie, а потім через UNWIND розгортаються жанри та зв'язки [:HAS_GENRE]. Завдяки MERGE і IF NOT EXISTS (з попереднього кроку) скрипт можна запускати повторно без дублікатів.

**3 — Запити різної складності**
1. Що означає довжина шляху в даному контексті?
Оскільки у нас є два типи вузлів (User і Movie) і ребра [:RATED] з'єднують саме User із Movie:
* 1 ребро переводить нас із User у Movie.
* 2 ребра проходять через 1 спільний фільм між двома користувачами: User A -> Movie 1 -> User B.

2. Один хоп — це один крок по ребру RATED, а значить — шлях довжини 2 означає, що два користувачі оцінили один і той самий фільм.
Так. Це означає, що двоє користувачів оцінили один і той самий фільм (Movie X) — тобто вони пов'язані безпосередньо через один спільний фільм без проміжних користувачів.

3. Як інтерпретувати шлях довжини 4? Довжини 6?
Довжина 4 — два користувачі пов'язані через 1 проміжного користувача та 2 спільні фільми (User A -> Movie 1 -> User B -> Movie 2 -> User C).
Довжина 6 — два користувачі пов'язані через 2 проміжних користувачів та 3 спільні фільми (User A -> Movie 1 -> User B -> Movie 2 -> User C -> Movie 3 -> User D).

**4 — Виявлення супервузлів**
1. Які вузли виявилися супервузлами? Скільки у них зв’язків?
* Користувачі (:User, ребра [:RATED]): медіана становить 96 оцінок, але є активні «хаби», зокрема userId = 4169 (2 314 зв’язків), 1680 (1 850), 4277 (1 743), 1941 (1 595) та 1181 (1 521).
* Фільми (:Movie, ребра [:RATED] та [:HAS_GENRE]): медіана — 123.5 оцінки, але культові фільми мають тисячі ребер: American Beauty (1999) — 3 430 (3 428 [:RATED] + 2 [:HAS_GENRE]), Star Wars: Episode IV — 2 995 (2 991 + 4), Star Wars: Episode V — 2 995 (2 990 + 5), Star Wars: Episode VI — 2 888 (2 883 + 5).
* Жанри (:Genre, вхідні ребра [:HAS_GENRE]): найбільшими «концентраторами» фільмів є Drama (1 603 зв’язки) та Comedy (1 200), далі Action (503), Thriller (492) і Romance (471).

2. Чому запит, що зачіпає такий вузол, працює повільніше, ніж запит по «звичайному» вузлу з тими самими індексами?
Індекс допомагає швидко знайти стартовий вузол (наприклад, за userId, movieId або name), але далі починається обхід графа:
* Комбінаторний вибух проміжних збігів: коли запит проходить через вузол із тисячами ребер, рушію доводиться розгортати та перевіряти набагато більше сусідів і шляхів, ніж для вузла з 20 – 100 зв’язками.
* Більше роботи в WHERE, агрегаціях і shortestPath: кожне зайве проміжне ребро додає рядків у конвеєр виконання, збільшує обсяг пам’яті під проміжні колекції/агрегації та розширює фронт пошуку під час обходу шляхів.

**6 — Аналіз і висновки**
1. Граф vs SQL. Які із запитів частини 3 було б складно або неможливо написати в SQL? Чому? Наведіть конкретний приклад — покажіть, як виглядав би еквівалентний SQL-запит (або поясніть, чому його не існує).
У класичному SQL без рекурсії неможливо написати запит для довільної невідомої глибини ланцюжка зв'язків.
У стандартному реляційному підході кожен додатковий «місток» User -> Movie -> User вимагає нового самоз'єднання (JOIN) таблиці ratings, тобто глибина пошуку фіксується жорстко на етапі написання запиту.

2. Де граф програє? Для яких задач із цим датасетом реляційна модель підійшла б краще? Наприклад: агрегація по всіх користувачах, звіти, експорт даних.
Графова база (як-от Neo4j) найкраще розкривається там, де головне — обхід зв'язків і пошук шляхів/спільнот. Натомість реляційна модель (SQL) виграє в таких сценаріях для цього датасету:
* Глобальні масові агрегації по всіх даних та аналітичні звіти: наприклад, підрахунок загальної статистики по всіх 1 000 209 оцінках, розподілу оцінок за віковими групами та професіями, зведені таблиці чи фінансові/операційні звіти.
  Колонки та таблиці в SQL оптимізовані під сканування й масову групування/агрегацію мільйонів рядків.
* Експорт табличних вибірок і ETL / BI-інтеграція: коли потрібно вивантажити «плоску» таблицю, реляційна таблиця або аналітичне сховище робить це природніше й без зайвого формування графових структур.
